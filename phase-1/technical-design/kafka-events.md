# Kafka Events — Phase 1

**Status:** Complete  
**Source of truth:** [BRD v1.4](../requirements/BRD.md)

Event envelope conventions, schema registry, consumer idempotency template (including processing flow diagram and per-family step patterns), DLQ topology, and BACKWARD compat protocol: see [conventions/kafka-events.md](../../conventions/kafka-events.md).

Consumer group tables below list **Side effects** (the unique business logic per group). For the generic processing loop and retry/DLQ rules, see conventions §4. The **Pattern** column maps each group to its family pattern in conventions §4.2.

MongoDB audit collection schemas (`audit_logs`, `activity_events`): see [data-model-mongodb.md](data-model-mongodb.md).

**Every field below is there because a consumer writes it.** The field-by-field account — each consumer group, each field it must write, and the payload field that supplies it — is [consumer-field-matrix.md](consumer-field-matrix.md). A payload gains a field only when that matrix names the consumer it serves, and loses one only when no row needs it. The matrix is also the check that closes in the other direction: for every field in an Elasticsearch mapping, an email template or a MongoDB collection, it names the payload field that fills it.

**Schema revision state.** Every schema in this catalogue is at `event_version: 1` and **none has been registered**: no CI run has pushed a subject to the Schema Registry and no consumer exists that holds a previous schema. Corrections to these payloads are therefore amendments to the initial version rather than evolutions of a live one — `event_version` stays at `1`, and no `.v2` topic is created ([conventions § 2](../../conventions/kafka-events.md#schema-registry)). From the first registration onward the `BACKWARD` rules bind: an added field carries a default, a removed field is drained consumer-first, and a rename or retype is a new topic.

**Envelope.** Every event in this catalogue carries the full envelope — `event_id`, `event_type`, `event_version`, `occurred_at`, `correlation_id`, `payload` — per [conventions/kafka-events.md §1](../../conventions/kafka-events.md#event-envelope), which owns the envelope shape and the Avro record namespace: every schema below declares `"namespace": "com.aliceut.events"`, flat, with no per-domain suffix. This catalogue owns the topic names, the event type names and the `payload` record of each event, and nothing else about the envelope. `correlation_id` is the value propagated from the inbound `X-Correlation-ID` header, generated by the API when the header is absent, per [conventions/observability.md — Correlation ID](../../conventions/observability.md#correlation-id). A scheduled job with no inbound request generates one `correlation_id` at the start of the run and reuses it for every event that run emits.

**Producer contract.** Every producer writes its outbox row **in the same Postgres transaction** as the domain change the event describes — never after commit. The row populates `key`, `aggregate_id`, `aggregate_type`, `event_type`, `event_version`, `payload`, `correlation_id`, `created_at` and `updated_at`; `key` is the partition key named in each topic's property table and equals the aggregate id, so per-aggregate ordering holds. The `platform` outbox relay is the only writer to Kafka.

**Consumer contract.** Every consumer group deduplicates on `platform.processed_event (consumer_group, event_id)`, commits its Kafka offset **after** the side effect completes, and routes failures to its own DLQ topic ([§4](#dlq-topics)). Every `<topic>-value` subject is registered with `BACKWARD` compatibility (BRD §12 #9); a new payload field is added as a union with `null` carrying a default, per [conventions §6](../../conventions/kafka-events.md#backward-compatibility-protocol).

**Enum defaults.** Every enum below that classifies something extensible — a reason, a source, a category, or a status that could plausibly gain a value — carries an explicit `UNKNOWN` symbol and declares `"default": "UNKNOWN"`, and any enum added to this catalogue later does the same. Appending a symbol is BACKWARD-compatible as far as the registry is concerned, but a reader still holding the previous schema **fails to decode** the new symbol unless the enum declares a default to fall back to, and that default is only worth anything if it was in the schema *before* the first symbol was appended — so it goes in when the enum is defined, not when it grows. The default is never a real business value: a reader degrading a new `SHIPMENT` to `UNKNOWN` writes a record that is visibly incomplete, while one silently reading it as `MANUAL_UPDATE` writes a wrong audit record nobody goes looking for. V1 deploys the whole monolith in one release, so no reader ever lags its producer and this is precaution rather than a live defect; it is stated here so it is not removed later as pointless. Enums whose symbols are logically exhaustive are exempt — `KycDecision` (§2.2) and `PlacementOutcome` (§2.8), where a third symbol would mean a different field rather than another value.

**Search projection.** No event carries a complete Elasticsearch document, and none is meant to. Product content belongs to Catalog, prices to Pricing, stock to Inventory, seller state to Seller, so an event that carried the whole document would have to read another module's tables. Each event therefore carries the full set of fields **its own domain owns**, and every `search.*` group applies its event as a partial document update, never a whole-document write. The mechanism performing that update is chosen per consumer, not shared by all of them: a `doc` merge with `doc_as_upsert` for the product-level fields, a scripted `_update` where the write addresses one entry inside `offers[]` — a `doc` merge cannot address a single element of a nested array, and a `doc` write carrying `offers` would replace the array and drop every co-seller's entry — and a scripted `_update_by_query` where the payload names offer ids or a currency and the consumer holds no product id to address. Which consumer uses which is specified in [api-design/search.md](api-design/search.md#write-mechanisms); all three write only fields the event owns and differ solely in how they reach the document. Not every write may create one: only the consumers whose event can legitimately be a document's first arrival upsert, so among those first-write ordering does not matter — whichever arrives first creates the document and later ones merge into it — while the rest describe a change to something published earlier and so are never the first event for a document. A `search.*` consumer never reads another module's tables and never makes an enrichment call to fill a gap; a field it does not own simply stays as the owning event last left it. No `search.*` group assumes the index is simply there: the Search module runs an idempotent `ensureIndex` during `workers` boot, creating `products` with the mapping from [api-design/search.md](api-design/search.md) if it is absent and warning on mapping drift rather than mutating a live index, and every `search.*` group starts consuming only after that step reports done — a first event must never be the thing that creates the index, because an upserting write against a missing index would take Elasticsearch's dynamic mapping instead of the declared one. The per-event field ownership map lives in [api-design/search.md](api-design/search.md).

**Consumer groups**

| Consumer group | Pattern | Side effects |
|---------------|---------|--------------|
| `notification.fulfillment-placed` | `notification.*` | Creates in-app notification for buyer (type `ORDER_PLACED`). No email (covered by `order.finalized` ET-01). |
| `notification.fulfillment-seller-alert` | `notification.*` | Sends ET-17 to `seller_email` from the payload. `ship_by` is included directly in the payload (placed_at + `fulfillment_window_days`, computed at checkout). |
| `platform.audit` | `platform.audit` | Writes `activity_events` (entity_type=`FULFILLMENT`, entity_id=fulfillment_id, actor_id=buyer_id, actor_role=`BUYER`). |
| `inventory.fulfillment-placed` | `inventory.*` | Publishes the availability change the checkout transaction has already applied. The `stock_reservation` rows and the matching `reserved_qty` increment are written synchronously inside the checkout transaction — the one synchronous inventory write the module boundary grants — so this consumer's only side effect is the `inventory.changed` outbox row (`change_reason = RESERVATION`) carrying the post-reservation `available_qty`, which is what moves the figure into Elasticsearch. It does **not** change `stock_reservation.status`: a reservation belonging to a placed fulfillment stays `ACTIVE`. Idempotent on `event_id` — a redelivery finds the id in `processed_event` and writes no second outbox row. |

**Reservation lifecycle boundary.** Every transition out of `ACTIVE` is written by an `inventory.*` consumer or by the reservation-expiry sweep, never by the Orders module, and each has exactly one writer: `CONSUMED` when the fulfillment ships ([§2.5](#25-fulfillmentshipped)), `RELEASED` on seller cancel ([§2.16](#216-fulfillmentcancelled)) or on refund of a `PENDING` fulfillment ([§2.7](#27-fulfillmentrefunded)), `EXPIRED` when the TTL sweep reclaims an abandoned checkout ([§2.19](#219-inventoryreservation_expired)). Placement is not one of them, which is why the consumer above leaves the status alone. The lifecycle and its single-writer rule are stated with the schema in [data-model-erd.md — `inventory.stock_reservation`](./data-model-erd.md#table-inventory-stock-reservation).

### 2.9 `order.completed`

Fires when **zero non-DELIVERED fulfillments remain** under the `order_id`, whatever the fulfillment count. A single-fulfillment order completes on its one delivery.

| Property | Value |
|----------|-------|
| Partition key | `order_id` |
| Producer | Orders module (completion check triggered by the `orders.delivery-tracker` consumer, §2.6) |
| Event version | 1 |

**[DESIGN DECISION]** The completion check belongs to the Orders module, which owns the `orders` schema; it is triggered by `fulfillment.delivered` and is never a raw `SELECT COUNT(*) FROM orders.fulfillment …` issued from outside that module. Orders evaluates its own fulfillment set and writes the `order.completed` outbox row in the same transaction as the evaluation. This avoids a dedicated "checkout session" table and keeps the rule in one place.

Terminal statuses count as settled, not pending:

| Fulfillment set | Emits `order.completed`? |
|---|---|
| All DELIVERED | Yes |
| All terminal (DELIVERED / REFUNDED / CANCELLED) with at least one DELIVERED | Yes |
| All CANCELLED and/or REFUNDED, none DELIVERED | No — the order settles on the derived `CANCELLED`/`REFUNDED` status instead |
| Any PENDING or SHIPPED remaining | No — not yet complete |

`order.completed` is a **notification signal only**. It writes no order status: the order-level status is derived from the fulfillment statuses on every read and is never stored, so no consumer of this topic — or of any topic in this catalogue — writes an `orders.order.status` column.

**Consumer groups**

| Consumer group | Pattern | Side effects |
|---------------|---------|--------------|
| `search.inventory-changed` | `search.*` | Updates `available_qty` and the `inStock` flag — **except on `change_reason = SHIPMENT`, where the write is suppressed**: shipment decrements `on_hand_qty` and `reserved_qty` together, so `available_qty` is unchanged and an update would rewrite the document to the value it already holds ([api-design/search.md](api-design/search.md#write-mechanisms), [consumer-field-matrix.md § 3](consumer-field-matrix.md)) in Elasticsearch. |
| `platform.audit` | `platform.audit` | Routes on `payload.change_reason`, to two different collections. `MANUAL_UPDATE` and `BULK_UPDATE` — a person changed a quantity — write **`audit_logs`** (action=`STOCK_ADJUSTED`, entity_type=`OFFER`, entity_id=offer_id, actor_id=seller_id, actor_role=`SELLER`), retained two years. `RESERVATION`, `SHIPMENT`, `REFUND_RESTORE` and `CANCEL_RESTORE` — system consequences of a buyer or seller action that is itself recorded elsewhere — write **`activity_events`** (entity_type=`INVENTORY`, entity_id=offer_id, actor_role=`SYSTEM`), retained ninety days. `adjustment_reason` is written through unmasked wherever it is present — operator-authored text about the operator's own stock, not a secret. The reason is retention, not taxonomy: `audit_logs` keeps two years and `activity_events` ninety days, and the stock trail is what a disputed quantity is reconciled against, so a human adjustment has to survive longer than a quarter. A reservation or a shipment movement does not need that window — the order it came from is recorded in `audit_logs` in its own right. A new topic does not adopt payload-based routing without the same retention argument behind it.

### 2.25 `listing.flagged`

Fires whenever a `moderation_case` is opened against a live listing. Two producers, one topic:

| Producer path | `source` | Trigger |
|---|---|---|
| Administration module — `POST /admin/moderation` | `ADMIN_MANUAL` | An admin flags a listing by hand and supplies a reason. |
| Seller module — `PATCH /seller/products/:id` and offer edit | `KEYWORD_MATCH` or `PROHIBITED_CATEGORY` | The edit trips the keyword blocklist or the prohibited-category guard. |
| Seller module — `POST /seller/offers` | `KEYWORD_MATCH` | The new listing's content matches a term whose `enforcement` is `FLAG` — the soft tier. A `BLOCK` term or a prohibited node `422`s instead and produces no event. |

**Auto-flag on edit: the edit commits, then the listing is flagged.** The edit is persisted (HTTP 200 with the updated resource plus a `warnings[]` entry) in a transaction that also sets `catalog.offer.status = FLAGGED` with `status_changed_reason = 'AUTO_MODERATION'`, opens the `moderation_case` row with `source = 'KEYWORD_MATCH'` or `'PROHIBITED_CATEGORY'` and the tripped terms in `matched_terms`, and writes this outbox row. That path is `POST /seller/offers` ([api-design/seller.md](api-design/seller.md#offer-create-screening)); `POST /seller/products` screens the same content but opens no case, because `moderation_case.offer_id` is required and a product with no offer is not a listing. ### 2.26 `pii.accessed`

Fires when one person reads another person's personal data. NFR-09 requires those reads to be logged; three Phase 1 reads qualify — a seller opening the order detail view that shows the buyer's unmasked shipping address (US-S-05b, `user-stories/seller.md`), an admin opening a KYC document during review (BRD §8 NFR-09), and an admin opening the seller detail view, which returns the seller's `tax_id` in full ([api-design/admin.md](api-design/admin.md)).

**No notification consumer and no search consumer, both deliberate.** Search holds `offers[].seller_active`, which is still `false`: the seller remains suspended and their offers remain `INACTIVE`, so there is nothing to write and no `offer_ids` in the payload to write it to. Notification has no template — ET-01…ET-21 is the complete V1 set and none of them announces a change to a suspension's terms — so the seller learns the new date from the portal banner, which renders the live column. That is a stated decision rather than an omission: adding the consumer later needs a new `notification.*` group and DLQ, and no change to this schema, because every field such a template would render is already carried and defaulted.

Adding this topic therefore moves the topic count and neither the group count nor the DLQ count: it joins the `platform.audit` group's subscription list, exactly as §2.27 did.

<a id="topic-retention"></a>
## 3. Topic partitions, replication and retention

**Every topic in §1 is created with 1 partition and replication factor 1**, DLQ topics (§4) included. V1 runs a single-node broker, so RF 1 is the only value available, and partition count is a throughput question rather than a correctness one at this scale. Ordering is unaffected: per-aggregate ordering comes from the outbox `key` being the aggregate id, so raising the partition count later is a topic-configuration change and not a redesign — the keys already place every event of one aggregate on the same partition. No topic states its own partition count; this is the single statement of it.

Default retention is **7 days** for every topic in §1 — long enough to replay a consumer through a weekend outage, short enough that the broker is not an archive. The MongoDB collections, not Kafka, are the durable record. The broker pins it rather than inheriting the image default: `KAFKA_LOG_RETENTION_HOURS=168`.

**Dedupe retention must be strictly greater than log retention.** `platform.processed_event` rows are kept for `PROCESSED_EVENT_RETENTION_DAYS=14` against the broker's 168 hours, and the inequality is the point, not the two figures. A `processed_event` row exists to make a redelivery idempotent, and redelivery has two sources: a rebalance or an uncommitted offset, which replays within minutes, and a deliberate offset reset or DLQ replay, which can replay anything still in the log. If the dedupe row expires first, replaying a week-old message finds no row and applies the side effect a second time. Equal values race. When either figure changes, the safe direction is to raise the dedupe window, never the log window.

One topic family overrides the default — `auth.*`, all three of it — and the table splits by reason rather than by family:

| Topics | Retention | Reason |
|---|---|---|
| `auth.email_verification_requested`, `auth.password_reset_requested` | **24 hours** | The payload carries a raw single-use credential token (§2.22, §2.23). The token's own TTL is shorter still (60 minutes for password reset, US-S-12), so nothing is lost by expiring the message early, and the window in which a broker-log reader could replay a live token closes with it. |
| `auth.password_changed` | **24 hours** | No token in the payload, but it is a user-credential topic and is held to the same window so the `auth.*` family has one rule rather than two. |
| Every other topic in §1 | 7 days | — |

Retention is set per topic at creation time by the `kafka-init` container in [docker-compose-topology.md § 6](docker-compose-topology.md#docker-compose-yml), not left to the broker default: broker auto-creation is disabled, because an auto-created `auth.*` topic would take the broker's seven days and hold a live credential token for seven times the intended window. Every value is env-configurable.

**A DLQ's retention is the *longest* of its source topics', not the shortest.** A DLQ is per consumer group, and one group — `platform.audit` — consumes both the 24-hour `auth.*` topics and every 7-day topic, so "follows its source topic's retention" has two answers for `platform.audit.dlq`. It is created at **7 days**. Provisioned at 24 hours instead, a failure while writing an `audit_logs` document for a `seller.kyc.submitted` event would become unreplayable after a day, and the loss would be silent — the DLQ alert fires on a non-empty topic, and an expired message leaves an empty one. The auth payloads reaching that DLQ are the masking consumer's problem and not the retention's: the token they carry has a 60-minute TTL of its own and is dead long before either window closes. Every other DLQ has one source retention and takes it.

**Three DLQs therefore take 24 hours, and they are named here rather than left to be inferred:** `notification.email-verification.dlq`, `notification.password-reset.dlq` and `notification.password-changed.dlq`. Each of those groups subscribes to exactly one topic and that topic is a 24-hour `auth.*` one, so the longest source retention *is* 24 hours. A dead-lettered message carries the original payload ([conventions §5](../../conventions/kafka-events.md#dlq-topology)), which on these three means a raw `verification_token` or `reset_token` — and a dead-lettered notification is precisely the case where a human opens the topic to find out why the email never arrived. Provisioning them with the other thirty-six would hold a live credential in the broker log for seven days on the one path guaranteed to be read by an operator. `kafka-init` creates them from `KAFKA_AUTH_TOPIC_RETENTION_MS` in a second loop for that reason ([docker-compose-topology.md § 6](docker-compose-topology.md#docker-compose-yml)). The remaining thirty-six consumer-group DLQs and `email.outbound.dlq` take seven days.

<a id="audit-masking"></a>
## 5. `platform.audit` consumer masking

The `platform.audit` consumer group masks before insert. Any `payload` key matching `DEFAULT_SENSITIVE_KEYS` in [conventions/observability.md](../../conventions/observability.md#nestjs-logger) — `password`, `token`, `authorization`, `cookie`, `tax_id`, `secret`, `refresh_token` and the rest of that list, matched case- and separator-insensitively at any nesting depth — is written to MongoDB as the literal string `"***"`.

**This is mandatory, not best-effort.** Two payload families in this catalogue depend on it:

- `auth.email_verification_requested` (§2.22) and `auth.password_reset_requested` (§2.23) carry a **raw single-use token**, because the notification consumer cannot build the email link otherwise and reading `identity.email_verification_token` from the notifications module would be a cross-schema read. `audit_logs` is retained for two years; an unmasked copy would outlive the token by that whole period.
- `seller.kyc.submitted` (§2.1) and `seller.kyc.decided` (§2.2) carry seller business identifiers including `tax_id`.

The mask is applied by the consumer, on the way into the document — never by the producer, which would deny the notification consumer the token it needs. The envelope fields (`event_id`, `event_type`, `event_version`, `occurred_at`, `correlation_id`) are never masked; they are what makes the record traceable back to the request that caused it.
